# 2. Feature Specification

## 2.1 Case Management
Users can create cases, provide a title and summary, add events, save, reopen, export, and delete cases. Case IDs are generated by the application.

## 2.2 Evidence Intake
Supported initial event types:
- `message`
- `call_summary`
- `url`
- `qr_payload`
- `payment_request`
- `payment_attempt`
- `note`
- `other`

Each event includes a timestamp, channel, user-provided description/payload, and source type. User-entered call summaries are explicitly labeled as summaries, not verified recordings/transcripts.

## 2.3 Timeline
- Sort events chronologically.
- Show event type, channel, timestamp, source, and key extracted fields.
- Show analysis indicators alongside events.
- Permit adding events and rerunning analysis.
- Handle missing/ambiguous timestamps without inventing precision.

## 2.4 Multi-Agent Investigation
Show agent status, structured output, evidence references, confidence/uncertainty, and errors. The UI must make it clear which findings are user-provided, parser-derived, rule-derived, or model-generated.

## 2.5 Temporal Evidence Graph
Graph nodes represent events and extracted entities when supported. Edges represent grounded relationships such as:
- same URL/domain referenced
- same recipient identifier
- temporal sequence
- repeated request/amount
- channel transition
- semantic claim/action relationship
- explicit user-provided relation

Each edge must include relation type, supporting evidence, and confidence. Do not create unsupported links merely because events are close in time.

## 2.6 Scam Journey Investigation
The investigator should:
- identify candidate pattern(s), not assert certainty;
- describe the sequence in ordered steps;
- cite event IDs and evidence IDs;
- note missing evidence and alternative explanations;
- distinguish observed facts from inferred relationships.

## 2.7 Risk Assessment
Allowed labels:
- `LOW_CONCERN`
- `CAUTION`
- `HIGH_CONCERN`
- `INSUFFICIENT_EVIDENCE`

Risk logic must be documented and calibrated on synthetic examples. Avoid implying a probability of fraud unless validated calibration exists.

## 2.8 Recommendations
Recommendations should be proportionate, e.g. pause, do not open unknown links, verify independently through an official channel, do not share PIN/OTP, and contact the bank/payment provider through a trusted official route if a payment may have occurred. Do not claim the system can reverse a transaction.

## 2.9 Demo and Evaluation
Provide synthetic scenarios with expected labels and a reproducible evaluation command. Show project-wide metrics on the Analytics page, with dataset scope and limitations.

## 2.10 Export
Export a user-reviewed case report as Markdown or JSON. Include timeline, evidence, graph relations, assessment, uncertainty, and disclaimer. Exclude secrets and avoid unsupported claims.
